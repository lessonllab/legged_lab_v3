# 支撑转换接口第二阶段：偏航与臂腿协调修正

用户要求：检查偏航和摆臂协调为何退步，修改后再训练1000轮，并结合play与原14700、第一阶段15700比较，保留正常步态。

2026-10-20 公开发布：[方法与复现命令](../support_transition.md)、[配对评估与视频来源](../../artifacts/support_transition_stage2/README.md)、[在线播放](https://lessonllab.github.io/legged_lab_v3/support_transition_stage2/)。下文 `.runtime/` 和 localhost 地址为实验当天的本机记录，公开副本以这些链接为准。

## 训练前诊断与修正假设

第一阶段新分支可对29个关节增加独立修正。实际过桩记录中，右肩俯仰长期额外向后约0.94度、腰侧倾约向一侧0.95度，左右髋和踝也有持续偏置。角度上限只能限制幅度，不能保证保留原有步态相位和左右协调。详细统计见`.runtime/support_transition14700_stage2/pretrain_action_diagnosis.json`。这是观测性证据；不能仅凭偏置断言每个关节的因果作用。

第一组冻结模型干预只取消新增手臂修正。已有64个桩路例仍全部到达；左臂与对侧脚步频范围相关性约0.432→0.588，右臂约0.282→0.200；终止时朝向误差约1.85→1.57度。取消手臂修正并不能同时改善两侧协调，需要继续检查下肢和躯干修正的作用。

第二组取消全部手臂、腰部与髋偏航残差，只保留腿部俯仰/侧倾。64/64仍到达，但整段偏航约2.51→5.12度，左右协调约0.432/0.282→0.678/0.304。这个干预暴露出腰髋补偿与腿部修正的相互作用，因此拒绝直接把十关节方案用于续训，保留腰髋控制权限。

另一个结构问题：第一阶段预测编码器与预测头同时接受PPO和事件监督梯度，预测表示可以被过桩奖励改变。第二阶段分开两个目标的梯度。这是待验证的干扰假设，并非已经隔离证明的根因。

按记录重建三个可观测奖励分量，原14700与第一阶段15700的过桩姿态惩罚率约为-0.00667/-0.00482，航向惩罚率-0.00319/-0.00441，偏航角速度惩罚率-0.01384/-0.01479。姿态项收益伴随方向项损失；这三项合计也没有改善，因而不能据此声称“总奖励偏好这种步态”。完整PPO回报还含其他奖励、未来价值与随机探索。详见`reward_subset_diagnosis.json`。本轮选择先修复附加动作的干扰，没有调整原运动奖励权重。

## 本轮设计

- 从第一阶段实验15700检查点继续，新增1000次PPO更新，结束于16700，4096环境。
- 原14700策略MLP和归一化持续冻结。原策略仍根据当前身体状态控制全部29个关节，包括自然摆臂；只保护手臂不叠加新残差，保留十二个腿部和三个腰部关节的修正。原策略继续动态控制手臂，并非锁住手臂关节。
- 预测特征传给残差时停止梯度；预测网络继续接受真实触地事件监督。辅助标签继续只用于训练，不增加推理真值输入。
- 原0.005残差幅度正则保留；新增0.02的批内平均残差软正则，减少持续偏置。它约束附加修正的均值，不规定姿态、摆臂幅度或固定迈步相位。
- 原运动、落脚、航向、停车奖励完全保留；原11700软保持项保留。续训时显式关闭冻结教师中继承的15700残差，保证教师仍是纯11700动作函数。
- 平地50%，桩路50%，保持正向/斜向路线、泛化类型和自动难度升降。桩路出生面对路线，给本体向前指令。
- 第一阶段15700参数和Adam全部继承；初始化动作因取消直接手臂残差发生显式变化，不能宣称与15700函数完全一致。冻结投影干预提供训练前对照。

三项修改共同构成工程修正，本轮无法单独归因于其中某个模块。腿部修正仍会通过闭环状态间接影响摆臂，冻结基础网络不等于保证物理轨迹不变。

## 验证

11项核心测试已通过，覆盖取消手臂残差后的初始动作一致、原有动态上身动作保留、PPO与预测梯度分开、教师无残差污染、Adam续训与保存加载、推理采集后正常重置，以及第一阶段的动作/标签时序检查。正式优化前运行原生事件采集与有限梯度预检，预检不做优化器更新。

训练后沿用同场景成对评估，分别比较14700、15700和16700的到达/停车、整段偏航、臂腿协调、身体晃动、步幅、步时、膝关节幅度、腾空与平地技能。旧1729种子已经参与诊断，不再作为本阶段独立新测试；预留新地图种子20261016用于最终同族泛化评估。

播放检查覆盖常规正向、斜向、泛化桩、平地前后退及相对退步明显的例子。视频若由Isaac轨迹重渲染，只表示真实Isaac物理轨迹重放，不能当作MuJoCo物理复验。

## 执行记录

首次原生预检通过标签与梯度检查，在第一轮优化之前因采样器将普通状态缓存重绑定为推理张量，导致退出推理上下文后的显式重置失败。修正为保持原缓存、原位复制新值，并增加跨推理上下文重置的复现测试。该启动尝试没有执行任何优化器更新；日志与状态保存在`startup_attempt1/`。重启仍从15700开始完整1000轮。

训练完成后的动作函数检查：门控关闭时，16700对同一组输入的确定性输出与14700逐位一致。已有地图32个平地回合的0.5–3秒窗口共4032帧，附加修正全部为零。整段平地轨迹中有97帧因临近地图边界、观察到空隙而打开门控，因此只能保证关闭时的函数一致，不能宣称所有平地位置都不触发修正。闭环物理轨迹仍有小幅差异，追加同一14700重复测试用于量化复位/数值波动；这次校准不做任何优化器更新。

## 1000轮完成后的配对结果

正式训练完成于16700，累计1000次更新，冻结14700基础网络检查通过。两组对照分别由64个已有地图和128个新地图回合组成；三种策略均全部到达并稳定停车。新地图生成种子20261016与已有地图栅格不同，但仍属于相同地形生成族。每组还含32个平地例。单个修正版因分别配对两种基线重复运行，不能把重复运行称为384张独立新地图。

相对原14700，按192个桩路回合等权汇总：

- 整段平均绝对偏航2.172°→1.699°，约下降22%；终止时绝对偏航1.373°→1.131°。
- 左臂与右脚步频范围相关性0.686→0.632，右臂与左脚0.232→0.284。协调性整体接近原模型，但两侧并未同时优于原模型。
- 身体晃动1.587°→1.678°，约增加6%。这是未解决的代价，不能称为稳定性全面提升。
- 同足步幅0.4896→0.4901m；相邻左右触地间隔0.3425→0.3551s；膝关节幅度46.55°→45.75°；交替触地比例均为1，过桩腾空帧比例均为0。节奏略慢，未出现明显缩步或跳跃。

相对第一阶段15700的直接配对：整段偏航2.604°→1.686°，约下降35%；左侧协调0.430→0.631，右侧0.279→0.285，后者没有明显改善。手臂关节速度RMS0.617→0.648rad/s，说明并非通过把手臂保持不动来恢复该指标。身体晃动1.356°→1.672°，同样是明确的取舍。

观测到的总/非手臂偏航角动量RMS比值从第一阶段0.841回到约0.757，接近原14700的0.747。它只表明该轨迹中的部分角动量抵消恢复，不能当作摆臂帮助稳定的因果证明。

已查看平地前进/后退、正向及斜向L10组合泛化、整段晃动与偏航退步最大的已有地图样本74，以及新地图固定正向46、斜向110、相对退步样本40的关键帧与短步态片段分帧。动作外观接近原模型，手臂仍会随步态活动；少数路线晃动较大，已补充到播放页，不只展示平均改善的例子。当前数值属于单训练种子的配对结果，不是完整论文结论。

已有地图中，直接取消新增手臂修正的冻结干预已经恢复了大部分左侧协调，但偏航仍约2.43°；修正后实际续训降到约1.62°。因此应区分直接关节投影的收益与其后的适应，不能把全部改善归因于预测分离或某个单一模块。

结果与原始记录：`.runtime/support_transition14700_stage2/aggregate_results.json`、各组`results.json`、`arm_audit.json`与`support_transition_audit.json`。交互报告为`http://127.0.0.1:8094/support_transition_stage2/`。

## 同模型重复校准与选择

同一14700按相同协议重复两次，64个桩路回合全部通过。整段偏航均值2.145°→2.229°，均值差+0.084°，单回合绝对差平均0.326°、95分位0.857°。身体晃动均值差+0.016°，左/右臂协调均值差-0.004/+0.003。这个重复对说明内部状态/复位/数值波动存在；它不是训练种子方差估计或统计置信区间。当前偏航与左臂的主要变化大于此次重复对的均值差，而右臂相对15700的微小变化仍不宜宣称提升。详见`repeat_calibration_summary.json`。

本轮保留14700为主基线，16700作为偏航更小、主要摆臂损失得到恢复的实验候选。步幅与交替迈步保住，身体晃动约增加6%仍需解决，不把这次实验称作全面胜出。未额外执行后续训练阶段。实时播放已使用16700、正向路线0、L10组合泛化变体7、0.75m/s和自动终点停车，保留手动指令切换；已核验至少连续4回合到达并停车、零失败。地址为`http://127.0.0.1:8095/`，运行与启动参数保存在`live_play_verified.json`及`live_play_launch.json`。这只是固定场景运行检查，不算额外独立泛化样本。
